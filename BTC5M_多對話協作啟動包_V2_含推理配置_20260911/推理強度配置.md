## 2. 模型與推理檔位分開記錄

「高」「極高」是本配置的建議推理標籤；「GPT-6 Pro」沿用本對話所討論的模型／模式稱呼，**不編成比極高多一級的通用 effort 值**。不提供不同產品之間的官方等價換算，也不沿用未核實的產品型號對照。實際能選什麼、選到了什麼，以使用者介面或可核對設定為準。

`REASONING_POLICY.json` 是本啟動包的協調設定，不是產品 API payload，也不會自行改動 ChatGPT、Codex 或其他客戶端。要記錄的是實際畫面／設定的原文字串；不能只因 prompt 寫「極高」就回報已啟用極高。

若無法讀到真實設定，actual 欄位填 `null`、確認狀態填 `UNKNOWN`。不能從回覆長度、等待時間或模型自述推測。使用者提供設定時，可記 `USER_REPORTED`，但不要改寫成工具已驗證。

若推薦的模式不可用，記錄可用的替代設定及理由。可以完成已有授權的有界準備或初稿，但重大裁決須標記仍待指定審查；不假稱設定相同或效能等價，也不藉此繞過工具或資料權限。

## 3. 每個角色把高階推理用在哪裡

### 00：把矛盾收斂為可執行的一個版本

先以極高對齊學生 V3 與 bridge／runner 的輸入、回報、來源和已驗收範圍；交付共同工作板後回到高。新衝突、整合架構或是否升級候選才重新升極高；可能改變整體研究方向時再做 GPT-6 Pro 專項審查。不要重新替每一條 lane 做一次全部研究。

### A：決定完整系統究竟該學什麼

第一輪建議直接以 GPT-6 Pro 審查教學／評分目標及其最強反例；日常機理分析以極高接續。交付應能回答 C 的訓練訊號與 D 的獨立反證，不把 Pro 時間拆成反覆微調小指標。零交易、縮量、多花錢、無價值成交與過度修復皆需被明確考慮。

### B：先設計狀態機，再按契約實作

極高用於責任、部分送出、UNKNOWN、晚到成交、取消等待和 Maker／Taker 共享工作的核心狀態機。確定接口、不變式及反例後，高負責隔離 patch、依賴封裝與原生驗證。程式與測試結果才是證據，不因使用 Pro／極高降低驗收。

### C：先檢查可表達性，不先增加模型規模

以極高核對 policy 真正使用的資訊，找出現有公式是否把需要不同處理的狀態壓成同一種決策。提出具體缺口後，涉及記憶／架構更換再做 GPT-6 Pro 審查。架構確定後，用高處理已定規格的訓練器接線與實作；不能每輪都從頭設計系統。

### D：關鍵審查保持足夠深度與獨立性

日常建集和核數用高；第一輪資料／畢業契約、洩漏、尺度取巧与正式否決用極高。先依原始證據與預定規則形成判斷，再對照 A／C 的解釋。換一個聊天或模型並不自動構成獨立驗證；也不能只用低強度讀設計者摘要，就替複雜設計背書。

## 4. 升級與回到實作的條件

升級理由限定在：證據有實質矛盾、方案遭具體反例擊穿，或即將改變共同學習目標、學生架構及核心帳務。缺檔、尚未 collect、依賴未封裝，先處理資料／工程，不反覆升檔空想。

每次極高／Pro 審查都交付：

**判斷 → 支持證據 → 最強反例 → 能區分假說的下一個實驗 → 可交給工程的規格。**

這是可分享的結論、證據與實验規格，不要求揭露內部逐步推理。審查完成即轉入有界實作／實驗；沒有新證據或新反例，不重開同一場整體審查。較高推理不取代精簡 CURRENT、版本指紋與交接。

## 5. 工作板與交接怎麼記

`WORKBOARD.template.json` 已為總控與每個任務加入 `reasoning_plan`，區分日常預設、任務初始建議、實際設定與待確認狀態。任務仍維持 `PROPOSED` 或原來的依賴阻塞，沒有因設定推理強度就啟動。

`HANDOFF.template.json` 新增 `reasoning_context`、`reasoning_sessions` 與 `review_deliverable`。每一段設計／實作／覆核記錄實際模型與檔位、設定來源、升級理由及對應成果；不同階段有換設定就分列，不把整個任務都寫成使用最高模式。欄位只記模型與工作設定，不收錄內部思考過程。

## 6. 推理資源與 worker 算力分離

極高或 Pro 不擴大 HFT／訓練額度、可寫檔案範圍、fresh／SEALED 資料權限或實單授權。重型建集、回放與訓練仍由唯一總控排程到第二台，初期同時一個重型 job、每個 `max_threads=4`，先 1–3 場 smoke 再 Stage-A ≤16。

`capital_cap=null`、真實成交與 ownership、禁止恢復舊 180 秒／Pair／TTL 環境硬閘門、不修改 8781 等規則原樣保留。B／C 使用不同模型或增加推理深度，也不因此取得額外寫入或派送權限。

## 7. 啟動與既有對話更新

新對話：先依此表在可用介面選擇建議模式，再貼對應的 `PROMPT_00/A/B/C/D`。每份提示詞開頭已內嵌該角色的設定摘要，即使只貼單一角色提示詞也不會漏掉配置；完整共用細節與模板仍以本包為準。

既有對話：只補貼角色提示詞開頭新增的「推理設定」段落，明確要求保留原 task_id、已完成結果與当前進度，不重跑專責任務。已有工作板／HANDOFF 使用新增欄位合併更新，**不要用空白模板覆蓋正在執行的工作板**。切換設定不能把既有 job 重設為未提交或造成重複派送。

若由總控將本配置放入共用協作目錄，只在已有寫入授權內複製 `REASONING_POLICY.json` 和本說明，並更新 CURRENT 的指向；本 ZIP 本身没有完成部署。
