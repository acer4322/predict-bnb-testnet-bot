# 一般研究的批次測試

使用者於 2026-09-21 明確要求：不只調參搜尋，一般機制對照、消融與執行情境驗證也優先批次化，以減少逐組派送、等待與人工彙整。此偏好不取消小測先行、每輪回報、重運算第二台、凍結規則與禁止重送未知工作等邊界。

2026-09-27 使用者再次要求提高並行數以縮短測試時間。對已凍結、互相獨立的市場路徑，確認 worker 容量及暫存／輸出目錄隔離後，優先在同一工作內使用最多 4 個單執行緒子程序，避免預設逐場串行。保留總計 max_threads=4；記錄實際並行數、記憶體餘量與耗時，再決定是否調整。遇到未知錯誤時停止啟動新格，收完已啟動的獨立格並保留證據，不自動重跑。通訊或收集時間與 native 執行時間分開報告。

## 執行與提出候選分離

- **固定測試矩陣**：先列好方案 × 市場／執行情境，例如原版／新機制、功能開／關、已核定的情境組合。每格完整測試，輸出成對比較。沒有自動調參、挑樣本或修改公式。
- **自適應搜尋**：由搜尋器提出候選，測試層仍可使用同一種保存／核驗接口。搜尋分數與驗收用途必須按各研究的凍結協議區分。

不要為批次而把有依賴的階段全部一次送出。先功能小測，再同一套已通過的接口做較完整矩陣；一批完成先彙整報告，沒有新的授權／已凍結安排不自動連跑其他輪。

## 可重用元件

`tools/research_case_batch_v1.py` 提供 `run_matrix(spec, out, execute, reuse, before_new, on_progress)`。

設定欄位：

```json
{
  "version": "RESEARCH_CASE_BATCH_V1",
  "execution_identity": {"policy_sha256": "<pinned>", "data_sha256": "<pinned>", "execution_contract_sha256": "<pinned>"},
  "arms": [{"id": "BASE", "config": {}}, {"id": "FEATURE_ON", "config": {}}],
  "cases": [{"id": "CASE_A", "parameters": {}}, {"id": "CASE_B", "parameters": {}}],
  "max_new_evaluations": 4
}
```

`execution_identity` 必須涵蓋會改變結果的程式、資料、模型／初始化、隨機種子與成交、費率、時鐘等假設；適配器負責明確核驗。以上僅 schema 範例，不能拿佔位值直接做正式研究。

元件本身不執行 shell、不查網路、不送交易、不啟動模型、不自動選擇下一個研究方向。各研究以受信任的 Python 適配器實作一個格子的完整測試。使用既有 strict LAN dispatcher 把適配器送到第二台，不重寫另一套派送服務。

## 結果與重用

每格先落盤 RUNNING，再執行或核驗重用；完成必須附 metrics 與至少一份證據 artifact 雜湊。`BATCH_STATE.json` 包含每格完成／失敗、執行來源、次數與結果；`PROGRESS.json` 包含完成數／總數、新執行數與重用數。

重用要同時核對：舊工作 COMPLETE、來源 identity／方案／情境一致、原 artifact 雜湊、必要的重新彙總恆等式。新的外層 runner 不必迫使不變的策略／撮合重新回放，但任何會改變決策或環境的改動，都必須改變 execution identity。新決策不可沿用原策略的未來成交路徑。

未知、中斷、失敗或不一致證據均停下保存，不自動重跑失敗格。caller 必須持有既有的單一 writer／job ownership lock；元件不取代執行層的 UNKNOWN／pending 管理。

報告一定要保留全部成對改善／惡化、兩個結算分支、pending 下界、實際支出、活動量與資料範圍；程式完成與策略通過是兩個狀態。

## 第一個實際接入案例

`data/research/btc5m_repair_service_pressure_full12_20260921_r89/`：固定 R89 NEW_ONLY × 原十二情境；核驗重用三個小測格，只允許九次新 native。實際狀態見該目錄 `CURRENT.md`，不可因範例存在就重新派送。

通過與否沿用 R85 的原七項門檻，另外逐情境比較候選37。不能把 R85 專用的「原三條正路徑」個數直接套給正路徑數不同的候選37。

## 驗證與操作

元件合成測試：`python -X utf8 tools/test_research_case_batch_v1.py`。這些不是市場回測。

一般擴展只需增加新的已核定矩陣和適配器，不需要每輪再建立一個批次框架。當前執行仍是一個 heavy job、max_threads=4；批次化不等於不限並行。標準 auto-collector 的 Console 仍作工作監控提示，但關窗也可能代表失敗／逾時，科學完成以結果核驗為準。

## 改善版本的後續係數搜尋

使用者進一步要求：有改善的機制版本，可以再做一次有限範圍調參批次，探索更好的收益／風險取捨。先完成固定機制與跨市場成對比較，再選少數可解釋係數、保留原版與零新增項對照；不得把未作用的機制當成只差倍率。用於提案／選版的市場均屬已消耗，後續驗收使用不同、未參與搜尋的市場，派送前另凍結。這是研究順序偏好，不是無條件自動連跑參數搜尋。
