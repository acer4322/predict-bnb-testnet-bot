## 2. 「被動修復處理不了」實際怎麼判斷

〔觀〕判斷程式在 `run_variant.py:419-424`：
- `wb7` 取的是 `state['owners']` 中所有弱邊 owner 的 limit。`state` 來自 `isolated_gate.snapshot`（`isolated_gate.py:12-20`），它收錄**所有非 TERMINAL 的 carrier**，不分路由（PASSIVE 或 ACTIVE）、不分狀態（包括 CANCEL_PENDING），剩餘量為 0 也照樣收錄。
- 判斷用的是**計畫前**的 `state`，不是 `planned`（`:393`、`:402`），所以同一幀剛排入的新被動單看不到。
- 「被甩開」的條件是 `(not wb7) or ask ≥ max(wb7) + 0.03`。

〔推〕所以答案是：**會混為一談。**
- 「完全沒掛單」「單子全部成交或已終結」「本幀剛要掛」都會落入 `not wb7`。
- 如果有一張撤單中的高價單，或一張已送出但未成交的主動單，它的 limit 會拉高 `max(wb7)`，反而壓住觸發。
- 如果弱邊買賣價差本身就 ≥0.03，就算我方掛在最佳買價，也會被判成「被甩開」。

另外，(b) 虧損擴大和 (c) 夠便宜兩個條件根本不看被動單狀態。〔觀〕觸發次數會重疊：151＋78＋11＝240，但實際送單只有約 183 次。現有 trace 的 events 列不含 owner 狀態，**要分類只能加新的記錄欄位**。

## 3. 換邊後 last_H 與 peak 的分支身份

〔觀〕
- `roles.strong` 就是 `side or 'UP'`（`roles_runtime.py:17-19`），換邊後立即跟著變。
- `ctx.peak = max(inv[當下strong] − cost)` 在每一幀累積，從不重設（`run_variant.py:37`）。
- `V12G_AR3['last_H']` 只在送單時寫入當下弱邊的 H（`:433`），同樣從不重設。
- 換邊之後，`t_def`（`:422`）拿「新弱邊的 H」去和「舊弱邊的 last_H」比較；`cash_capacity = worst_G − RETAIN × peak`（`economics.py:40`）裡的 peak 可能是舊強邊的高點。

〔推〕程式證據顯示，**換邊後分支身份確實不一致**。這是否造成實際損害，要用 trace 核對換邊前後的觸發和 cash_capacity 才能確定，目前是 **UNKNOWN**，還不能判定為 bug 的影響。准入規則 `admission` 也用同一個 peak（`economics.py:60`），所以重開准入規則時會繼承同樣的問題。

## 5. 核對 2629199 的更正，以及「修回再 ADD 失守」

**用 row.json 核對 v28 的更正**〔觀〕，來源是 `v12g28_AR4_R25_2629199/row.json`：
- **時間線：** 第 15.9 秒選 UP，第 17.7 秒換到 DOWN（UP 中價 0.365），第 300.7 秒換回 UP（已過結束時間）。所以 17.7 秒之後整場都是 DOWN 為強邊、UP 為弱邊。
- **主動修復的成交價：** active_births 共 18 筆，16 筆在 0.17～0.37，2 筆在 0.43（各 60 份），**沒有任何一筆在 0.8**。17.7 秒後主動修復買的一定是弱邊，也就是 UP。
- **v27「修復在 0.8 追 DOWN」的說法不成立。** 原因是 PADD 在 18.5～46.5 秒以 0.67～0.70 買了 14 筆、共 210 份 DOWN，那是選邊加倉，不是修復。
- **兩邊庫存都在同步增加：** 第 30 秒到第 240 秒，DOWN 從 300 增加到 2,042，UP 從 482 增加到 1,484；180～240 秒這段兩邊各增加約 515 份。被動成交 2,510 份，遠大於主動成交 1,015 份。
- **無法確認的部分：** births 沒有記錄方向，「16 筆 UP」是由弱邊定義推出來的，不是逐筆讀到；另外 PADD 的成交為什麼不在 births 裡，也是 **UNKNOWN**。active_requested 與 active_fill 相差 227 份（未成交或 EOF），現有檔案看不出屬於哪幾筆。

**「修回再 ADD 失守」的可推翻解釋**（每一條都附最小同根比較，同樣 10 場）：
1. **准入規則關閉（NOGATE），強邊的被動加倉抵銷了修復**（v28 的假說）。比較：AR4_R25 對 AR4_R25＋准入規則開啟。
2. **問題在過早換邊（選邊後 1.8 秒就換），而不是修復和加倉的協調。** 比較：同一設定下換邊門檻不變，但換邊後讓准入規則保護重新開始計算；或只看已換邊的場次和沒換邊的場次分開算。
3. **分支身份錯置**（第 3 項）**讓換邊後的觸發和預算失真。** 比較：換邊時重設 peak 與 last_H 的新組，其他全部相同。
4. **被動單遭逆選擇（v23 已觀察到）成為主要的加倉來源。** 比較：准入規則只擋強邊被動單，對照擋全部強邊單。

**重開准入規則會不會又停擺**〔推〕：**有高風險。**
- K=4.15 時，強邊加倉的 `delta = q × (1 − 5.15p)`，只要價格 p > 0.194 就是負值。
- 只要 worst_margin < 0（即 G＋4.15H 加上掛單懲罰為負，換邊後常見），`margin_ok`（`economics.py:59`）就會擋下幾乎所有 0.194 以上的強邊加倉。
- `guarded_decide`（`run_variant.py:269`）也會擋原生主動模組的弱邊單。
- `ctx.first` 在 PREPARE 模式下可以在 `observe`（`:38-50`）裡被設定，**不受 AR_AFTER_DECIDE 限制**。所以「要到選邊後才會觸發」沒有程式碼保證。
- 派工前應先唯讀核對 v27／v28 trace 裡的 `first.action`、`first.t`，和 DECIDE 的時間比較。
