## 1. 要回答的問題

原修復入口 `economics.proposal` 在「完整修復」付不起（`FULL_RESTORATION_NOT_AFFORDABLE`）時什麼都不做，直到部位惡化或反轉。V51 顯示 28/29 場在這時其實有「在收益保留條件內可付的部分修復」上界，而 2630303／2630045 的弱側修復後來被強側大量支出（主要是被動單）超過。

**假說 H1：** 在完整修復付不起時，立即做一筆「有限、獨立記帳」的部分修復，並把之後新增的已確認擴張轉成新的有限修復責任，可以降低反轉場的平均與尾部虧損，同時不明顯傷害未反轉場收益。

**對立假說 H0：** 部分修復只是把正分支收益轉成弱側持倉，反轉場虧損不減，或未反轉場收益被吃掉（重演 V40）。

## 3. 機制定義（第 1 階段要實作與測試的內容）

所有參數沿用凍結值：K=4.15、RETAIN=0.5、被動 15、PADD ask≤0.80、STOP290、延遲 250/250、零費用、保守排隊。**不新增百分比、秒數、冷卻或下單上限。**

### 3.1 出生條件（全部依當下可見資料）

1. 原入口 `proposal(...)` 對當前弱側（原 `roles`）回傳 `FULL_RESTORATION_NOT_AFFORDABLE`。
2. 沒有 ACTIVE 的 BPR 工單。
3. 部分數量 `q = floor_step(min(needed_qty, total_cap, visible_depth))`，且 `q·ask ≥ 1`（原最低金額）。`total_cap` 已含 `(worst_G − RETAIN·peak)/ask` 與 `net_unreserved`，所以收益保留條件不變。
4. 未達 290 秒；以送單時間＋250 ms 到達仍在市場結束前（補上尾盤到達檢查）。
5. 首張 BPR：無其他條件。之後的新工單：見 3.3 的「新責任」條件。

### 3.2 工單內容與生命週期

- 唯一 `work_id`、固定物理側（出生時的弱側 token，不隨 roles 改名）、出生快照（持倉、payoff、pending、owners、ask、depth、proposal 全行）。
- 有限目標：`target_qty = q`，`budget_cash = q·ask_at_birth`；限價不高於出生 ask（主動吃單，受可見深度限制）。
- 同側已確認成交抵扣剩餘量，且每筆 receipt 只抵扣一次；同計畫 NEW 與 pending 預先占用；`CANCEL_PENDING`／UNKNOWN **不**還原額度。
- 終止（照 qualified_work 的語義）：達標、實際 FLIP／方向改變、弱側已非負、強側已非正、淨方向消失、290 秒。終止只停止新 NEW，不抹除在途 owner；在途單保留到真實終態並計帳。
- **每張送出前都重跑 `admission` 的 reserve 檢查**（`worst_G − p·q ≥ RETAIN·peak`）。不通過就等待，不放寬。
- 與原主動單共用原「合計 5 張」主動上限，原 owner 與原合格工單優先；BPR 不擴大上限。

### 3.3 新責任（回答 V51 的「2.10 USDT 首次預算」問題）

- 只有在前一張 BPR 已終止，**且**自其出生以來強側已確認成交新增了擴張（強側 confirmed inventory 增加），才可出生新工單。
- 新工單數量上限 = `min(3.1 的 q, Δdebt / slope)`，其中 `Δdebt` = 當前 `−worst_margin` 減去前一張出生時的 `−worst_margin`（只計新增負債，≥0）。
- 因此整場 BPR 總量 ≤ 首張 + 各段「已確認擴張造成的新負債」；不會每幀重算預算無限再生，也不會把首張的小預算當成整場能力。
- 沒有新擴張 → 不生新工單（即使 proposal 仍付不起）。

### 3.4 與舊狀態的隔離（必驗）

- BPR 不設定、不重置 `ctx.first`、`ctx.first_active`、`ctx.prepare`，不寫入 `ctx.events` 的 eligible 計數。
- 原 `Context.check`、PADD、原合格修復與 qualified continuation 仍依**當前真實組合**自行判斷；不凍結成 V58 的時點或動作。
- BPR 成交會改變組合，因此後續原入口行為可能與 V58 不同；這是預期效果，要分開報告「BPR 直接現金流」與「其他路由變化」。

## 4. 階段與停止條件

### 第 1 階段：元件（本機、純 Python，不跑 native）
